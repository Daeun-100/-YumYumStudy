# 알림 등록 반복 및 공통 지연 진단 — 2026-10-27

## 확인한 원인

`addPushTokenListener`에서 `refreshPush → enablePush → getExpoPushTokenAsync`를 호출했다. devicePushToken 인자가 없으면 Expo가 네이티브 토큰을 다시 조회하며 토큰 이벤트를 다시 발생시킬 수 있다. 설치된 SDK의 TokenEmitter에도 이 재귀 호출에 대한 경고가 있다.

Supabase 로그 조회 당시 최근 15분에 register_friend_call_device 23,912회, Auth user 조회 23,949회, 함수 HTTP 429 4,564회가 기록됐다. 사용자 입력 알람 전송 횟수와 기기 등록 호출 횟수는 다르다.

## 수정

- 이벤트가 전달한 DevicePushToken을 Expo 토큰 교환에 직접 전달해 네이티브 재조회를 피한다.
- 동시에 발생한 자동 등록은 방별 진행 중 작업을 공유한다. 실행 중 토큰이 바뀌면 최신 토큰으로 후속 등록한다. 실패한 작업은 해제하여 다음 재시도가 가능하다.
- 포스트잇 조회/저장/삭제와 알람 함수 send/register/status/disable/config에 기존의 기기 로컬 시간 측정기를 연결했다. 토큰, 메시지, 사용자 ID는 기록하지 않는다.
- 기존 작업 트리의 초기 로딩/공부 시작 개선 및 측정 코드를 유지했다. 서버 인증, 기록 생성의 요청 ID, 재시도 동작은 변경하지 않았다.

## 서버 시간과 한계

조회 당시 최근 1시간의 x_envoy_upstream_service_time 평균/최대(ms):

| 요청 | 횟수 | 평균 | 최대 |
| --- | ---: | ---: | ---: |
| get_today | 203 | 22.2 | 282 |
| get_room | 205 | 22.5 | 308 |
| start_study | 15 | 32.3 | 109 |
| put_room_postit | 3 | 139.7 | 338 |
| call-friend 전체 액션 | 55,596 | 160.8 | 2,627 |

함수 시간은 대부분 등록 요청이며 알람 send만의 시간이 아니다. 이 값은 클라이언트 네트워크·인증 잠금·기기 감시 준비·이미지 로딩을 포함하지 않는다. DB 진단 당시 대기 중인 앱 쿼리/잠금은 관찰되지 않았다. 따라서 알림 요청 폭주가 확인된 결함이지만 모든 클라이언트 시간 초과의 유일한 원인이라고 단정하지 않는다.

## 검증 및 후속 실측

전체 테스트 119개 통과, npm run lint 및 npm run typecheck 통과. 네이티브 SDK 토큰 이벤트를 흉내 내 실제 push.ts 어댑터를 실행하는 회귀 테스트에서 네이티브 토큰 조회 1회 후 등록이 종료됨을 검증했다. 동시 실행 공유, 최신 토큰 후속 처리, 실패 후 재시도도 검증했다.

이 변경은 로컬 소스에만 적용됐다. 배포된 앱에는 아직 반영되지 않았고 실제 휴대폰 개선 시간은 측정하지 않았다. 새 번들/빌드 적용 후 기존 앱을 종료하고 앱 시작, 공부 시작, 포스트잇 저장, 친구 부르기를 같은 기기/네트워크에서 재측정해야 한다. getTimingSamples() 또는 EXPO_PUBLIC_PERFORMANCE_LOGS=true 설정의 콘솔에서 기존 startup.*, timer.*, rpc.* 및 새 postit.*, call-friend.* 표본을 확인한다. 알람은 실제 사용자 동작으로 전송하고 자동 진단에서 발송하지 않는다. Supabase의 등록 요청 및 429 건수도 함께 비교한다.
