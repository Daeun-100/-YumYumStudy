# 설계 및 구현 순서

## 구현 원칙

최대한 간단하게 구현한다. 4명이 쓰는 초기 MVP의 현재 요구사항을 기준으로 판단한다.

- Expo 공통 코드와 Supabase 기본 기능을 우선 사용한다. 별도 API·WebSocket 서버를 만들지 않는다.
- 미래 확장을 위한 다중 방, 범용 권한 체계, 플러그인 구조, 불필요한 계층을 미리 만들지 않는다.
- 파일·컴포넌트·공통 함수는 실제 복잡함이나 중복이 생길 때 분리한다. 라이브러리는 필요한 경우에만 추가한다.
- 친구 시간은 시작 시각으로 화면에서 계산하고 시작·중지 변경만 Realtime으로 받는다. 진입·재연결 시 DB를 다시 조회한다.
- UID 소유권, 중복 타이머 방지, 저장 실패 표시처럼 기록의 정확성에 필요한 처리는 유지한다.
- 미정 정책을 임의 구현하지 않는다. 자동 검사는 날짜 경계·권한·동시 요청처럼 오류 영향이 큰 부분에 집중한다.

## 구조

현재 `App.tsx`는 공통 시작 화면이다. 기능 구현 시 필요한 화면과 Supabase 연결부터 추가한다. 기능별 폴더와 도메인 계층을 미리 만들지 않는다. 플랫폼별 동작이 실제로 달라지는 부분만 `.web.ts`/`.native.ts` 등으로 분리한다.

클라이언트 → Supabase Auth/PostgreSQL RPC → PostgreSQL. Realtime은 화면 갱신 알림에 사용하고 최종 기록은 DB를 다시 조회한다. 별도 API 서버는 만들지 않는다.

Auth는 로그인 화면 없이 익명 인증에 사용한다. 실행 시 저장된 세션 복원을 먼저 시도하고, 세션이 없을 때만 익명 사용자를 생성한다. 일시적인 통신 오류를 세션 없음으로 취급해 UID를 반복 생성하지 않는다. UID와 인증 세션을 구분하며 UID만 전달해 소유권을 주장할 수 없게 한다. 세션은 플랫폼별 영속 저장소에 보관한다. 저장소 삭제·기기 변경 후 기존 UID 복구는 MVP 범위 밖이다.

방은 서버에 미리 준비한 하나만 사용한다. 프로필 초기화 RPC가 인증 UID를 고정 방에 멱등하게 등록하며 클라이언트의 방 생성이나 방 ID 선택을 받지 않는다. 작성자도 동일한 경로로 참여한다. 초대·가입 승인·4명 제한은 구현하지 않는다. 익명 인증 사용자의 고정 방 현황 조회와 자기 기록 변경을 RLS로 허용하고 세션 없는 요청 및 타인 변경을 거부한다.

진행 중 세션은 서버의 시작 시각부터 직접 중지 승인 시각까지 유지한다. 화면 이탈·잠금·프로세스 종료·통신 단절은 종료 사유가 아니다. heartbeat는 연결 표시용으로만 사용한다. 백그라운드 작업 없이 서버 시각과 시작 시각으로 경과 시간을 복원한다. 친구 화면도 같은 방식으로 진행 중 시간을 표시하고 확정 합계와 구분한다. 중지 통신 실패 시 미확정 상태를 표시하고 재시도하며 서버 승인까지의 시간을 포함한다.

## 제안 데이터 모델 (마이그레이션 미작성)

| 테이블 | 핵심 정보 |
| --- | --- |
| profiles | 익명 Auth UID(PK), 표시 이름, 고정 방 ID. 이름은 고유 키가 아님 |
| study_room | 사전 생성한 고정 방 하나. 클라이언트 생성·삭제 불가 |
| goal_versions | 사용자, 적용 시작 공부 날짜, 요일별 목표 |
| study_sessions | 사용자, 시작/종료 시각, heartbeat, 종료 사유, 멱등 요청 ID |
| daily_summaries | 사용자+공부 날짜 고유 키, 목표 스냅샷, 확정 공부 시간, 출석 결과 |
| leave_grants | 사용자, 지급 수량, 지급·만료 시각, 지급 근거 고유 키 |
| leave_usage / leave_allocations | 사용 날짜, 취소 상태, 어느 지급분에서 차감했는지 |

시각은 timestamptz, 공부 날짜는 date, 시간 합계는 정수 초로 저장한다. 진행 중 세션은 부분 unique index로 사용자별 하나만 허용한다. 세션 생성/종료, 연차 사용/취소는 RPC 트랜잭션으로 처리한다. 서버 함수의 실행 권한과 search_path를 제한한다.

공부 날짜는 서버에서 `(timestamp AT TIME ZONE 'Asia/Seoul' - interval '6 hours')::date`로 계산한다. 날짜 경계를 넘는 세션은 나누어 집계한다. 정산 작업은 중복 실행해도 결과가 같아야 한다.

## 단계

여러 세션에서 실행할 때는 [병렬 실행 안내](execution/README.md)의 순서·파일 소유권과 [공통 계약](execution/CONTRACT.md)을 따른다. 현재 실행 단위는 연결 상태를 앱의 Realtime 연결 여부로만 표시하고 구성원별 heartbeat는 보류한다. 기존 heartbeat 설명은 도입할 경우의 원칙이며 필수 구현을 의미하지 않는다.

1. 환경과 명세: 공통 실행, 타입 검사, 웹 export, 미정 정책 기록.
2. 정책 확정과 DB: 마이그레이션, 고정 방 초기 데이터, RLS, 테스트 UID, 트랜잭션 및 권한 검증.
3. 자동 진입과 목표: 익명 세션 생성·복원, UID 기반 프로필, 고정 방 자동 등록, 목표 버전, 공부 날짜 조회.
4. 타이머: 서버 세션, 연결 표시용 heartbeat, 이탈 중 누적, 복구, 중지 실패/재시도, 날짜 경계 테스트.
5. 친구 현황과 기록: Realtime, 재연결, 확정 합계.
6. 출석과 연차: 확정 정책 구현, 경계·중복 요청 테스트.
7. 배포 준비: 웹 manifest/아이콘/HTTPS, Android 서명 APK, 양쪽 실기기 검증.

PWA의 오프라인 캐시와 service worker는 초기 단계에 추가하지 않는다. 서버 승인 없는 공부 기록은 허용하지 않으며 이전 버전 캐시 문제를 줄인다. 홈 화면 추가는 별도 실기기 검증이 필요하다.

## 검증

환경 단계는 타입 검사와 웹 export로 확인한다. 도메인 구현 시 05:59:59/06:00:00, 장시간 세션, 목표 변경, 연차 만료, 중복 요청을 자동 검사한다. DB 단계는 실제 RLS와 트랜잭션을 통합 검사한다. 브라우저 이벤트와 Android 동작은 실기기로 확인한다.
