# 관리자 토스트 발송 기능 명세

작성일: 2026년 10월 29일

상태: 테스트 채널·서버 반영 완료 · 실기기 확인 대기

운영 인터페이스: 관리자와 Codex의 프로젝트 채팅

관리자가 원하는 시점에 특정 방 전체 또는 특정 사용자에게 앱 내부 토스트를 활성화한다. 서버에 안내를 저장하고 앱이 실시간 변경 신호와 재조회로 수신한다. 첫 적용 대상은 이미 만든 **‘업데이트가 준비됐어요’** 토스트다. 업데이트 문구와 디자인은 그대로 사용하며, 관리자는 어떤 업데이트를 누구에게 안내할지만 정한다.

여기서 ‘발송 성공’은 서버에 안내가 활성화됐다는 뜻이다. 사용자 앱의 실제 표시와 구분한다. 앱이 닫혀 있으면 즉시 표시할 수 없으며, 다음 접속 때 아직 유효하고 표시 조건에 맞는 안내를 보여준다.

## 1. 범위와 기본 결정

| 항목 | 이번 구현 |
| --- | --- |
| 운영 | 채팅용 스킬 → 운영 스크립트 → 관리자 전용 서버 함수. 별도 관리자 화면은 만들지 않음 |
| 대상 | 한 요청당 한 방. 방 전체 또는 그 방의 지정 사용자 목록 |
| 첫 토스트 | 기존 EAS 업데이트 토스트를 실제 앱에 연결 |
| 일반 안내 | 기존 공통 토스트를 이용한 `info_notice`도 지원. 업데이트와 독립적으로 활성화 가능 |
| 업데이트 문구 | ‘업데이트가 준비됐어요’ 고정. 제목·본문 입력을 받지 않음 |
| 일반 안내 문구 | 일반 안내를 요청할 때만 명시한 제목·본문 사용. 운영자가 주지 않은 문구를 만들어 발송하지 않음 |
| 시점 | 즉시 활성화 또는 시작·종료 시각 지정. 배포 후 뒤늦은 활성화 지원 |
| 수신 | 시작·복귀·재연결 시 조회 + 실시간 변경 신호 + 전경 주기 조회 |
| 반복 방지 | 사용자·방·설치 단위로 완료 상태 저장. 삭제한 안내는 복원할 수 없으며 다시 보내면 새 안내 ID 사용 |
| 앱 밖 알림 | 이 기능은 OS 푸시를 보내지 않음. 기존 푸시 발송과 별도 운영 |
| 업데이트 적용 | 기존 마이페이지 ‘적용하기’만 사용. 토스트 활성화·버튼 클릭으로 재시작하지 않음 |

지원하지 않는 토스트 종류·화면 이동·스타일·코드는 서버 입력으로 실행하지 않는다. 새 고정 템플릿은 앱 코드와 Storybook에 추가한 뒤 배포한다. 임의 HTML, JSX, 스크립트, 외부 URL은 허용하지 않는다.

## 2. 사용 시나리오

### 업데이트 배포 후 안내 켜기

1. 기존 master 배포 워크플로로 EAS 업데이트를 배포한다.
2. 관리자가 “이번 업데이트 1번방 안내 켜줘”라고 요청한다.
3. Codex가 배포 기록에서 정확한 업데이트 그룹, Android 업데이트 UUID, 채널, runtime을 확인한다.
4. 서버에 해당 업데이트 안내를 활성화한다. 그룹 ID와 플랫폼별 업데이트 ID를 혼동하지 않는다.
5. 앱이 안내를 조회한다. 해당 업데이트를 다운로드했고 아직 적용하지 않았으면 기존 토스트를 표시한다.
6. 아직 다운로드하지 않았으면 다운로드 완료 후 다시 조건을 평가한다. 이미 적용했으면 표시하지 않는다.

배포 전에 안내 설정이 없어도 된다. 이미 다운로드한 앱도 이후 서버 활성화를 받아 조건을 다시 평가한다. 단, 안내 수신 기능이 반영된 앱이어야 한다.

### 업데이트와 무관한 일반 안내

“1번방에 ‘오늘 밤 11시에 점검이 있어요’ 안내 띄워줘”처럼 명시한 일반 안내는 `info_notice`로 생성한다. 활성 상태의 대상 앱에 기존 공통 토스트로 표시하며, 업데이트 다운로드 여부와 무관하다. 특정 사용자 지정도 동일한 경로를 사용한다.

### 삭제와 다시 알리기

- “이 안내 삭제해줘”: 서버에 삭제 시각을 기록하고 수신 앱의 대기·표시 중 안내를 제거한다. 즉시 물리 삭제하지 않는다.
- 삭제한 안내는 다시 켜거나 복원할 수 없다. 생성·표시·삭제 기록과 중복 방지 이력은 보존한다.
- 다시 알리려면 새 요청 UUID와 새 안내 ID로 발송한다. 기존 안내와 별개의 안내이므로 이전에 완료한 설치에도 표시될 수 있다.
- 일반 안내 기본 유효기간은 활성화 후 24시간, 업데이트 안내는 7일로 한다. 다른 기간을 명시하면 그 값을 사용하며 운영 결과에 종료 시각을 표시한다. 최대 30일, 무기한은 지원하지 않는다.
- 시각은 한국 시간으로 입력·표시하고 서버에는 `timestamptz`로 저장한다.

현재 `pending: boolean`만으로는 지정한 업데이트를 구별할 수 없다. 또한 현재 토스트 store는 한 번 표시한 항목을 배경·차단으로 제거할 때도 완료 집합에 넣는다. 관리자 업데이트 안내를 단순히 `show()`에 연결하는 것만으로는 충분하지 않다.

## 4. 전체 구성

```text
관리자 채팅
  → 전용 스킬 → 운영 스크립트
  → admin-toasts 서버 함수
  → 안내·대상·감사 기록을 하나의 DB 트랜잭션으로 저장
  → 방 private 채널에 변경 신호

앱 시작 / 복귀 / 재연결 / 변경 신호 / 전경 주기 조회
  → 인증된 조회 RPC
  → 서버에서 방·대상·활성 기간 필터
  → 앱에서 템플릿·OTA·표시 환경·중복 상태 판정
  → 공통 ToastProvider
  → 기기 완료 기록 + 서버 관측 기록
```

DB 저장값이 기준이다. Broadcast는 재조회를 촉발하는 신호로만 사용한다. 개인 명단과 안내 본문을 방 채널에 보내지 않는다. private Broadcast의 채널 접근은 `realtime.messages` 정책으로 제어할 수 있다. [Supabase Realtime 권한 문서](https://supabase.com/docs/guides/realtime/authorization)

## 5. 데이터 모델

아래 이름은 구현 예정 이름이다. 기존 테이블·함수와 충돌 여부를 구현 단계에서 확인한다.

### `admin_toast_campaigns`

| 필드 | 의미와 제약 |
| --- | --- |
| `id` | 안내 UUID. 사용자 표시·중복 방지의 기본 식별자 |
| `schema_version` | 첫 버전은 1. 미지원 버전은 앱이 무시 |
| `kind` | `update_ready` 또는 `info_notice` |
| `room_id` | 실제 존재하는 방. 현재 앱의 0·1번방 지원과 일치시킴 |
| `audience` | `room` 또는 `users` |
| `deleted_at` | 삭제 시각. null이면 미삭제이며 삭제 후 복원 불가 |
| `starts_at`, `expires_at` | 서버 시간 기준 시작 포함·종료 제외 |
| `platforms`, `app_variant` | 지원 플랫폼 목록과 test/production 구분 |
| `min_capability_version` | 표시 기능 버전. APK 버전이나 OTA 리비전과 별개 |
| `payload` | 종류별 스키마로 검증한 JSON. 자유 구조를 허용하지 않음 |
| `revision` | 기존 앱 응답 호환용 정수. 삭제 요청의 조건으로 사용하지 않음 |
| `created_at`, `updated_at` | 서버 기록 시각 |

`update_ready.payload`에는 EAS project, channel, platform, runtime, update UUID, group ID, 배포 commit SHA와 참조 Release를 저장한다. 실제 비교 키는 **플랫폼별 update UUID**다. title·body·외부 링크는 허용하지 않는다. 첫 버전의 운영 OTA 대상은 Android이며 iOS는 실제 배포 경로가 생기기 전에는 거부한다.

`info_notice.payload`는 필수 `title` 1~60자, 선택 `message` 최대 240자의 일반 텍스트만 허용한다. 첫 버전에는 버튼이 없으며 기본 6초 표시 후 종료한다. 화면 읽기 사용 시 공통 토스트의 시간 연장 규칙을 따른다. 업데이트 토스트에는 이 시간제한을 적용하지 않는다.

### 추가 테이블

| 테이블 | 내용 |
| --- | --- |
| `admin_toast_recipients` | 선택 사용자 대상일 때 `(campaign_id, user_id)` 고유 행 |
| `admin_toast_requests` | 관리자 요청 UUID, 정규화 입력 해시, 작업 종류, 처리 결과. 중복 요청 방지 |
| `admin_toast_audit` | 발송·삭제 이력, 캠페인 revision, 관리자 인증 식별자, 결과·시각 |
| `admin_toast_receipts` | `(campaign_id, user_id, installation_id)` 단위 최초 표시·종료 시각과 종료 이유. 재전송해도 중복 집계하지 않음 |

방 전체 안내는 **유효기간 중 해당 방에 입장 완료한 사용자**를 대상으로 한다. 새로 입장한 사용자도 포함한다. 선택 사용자 안내는 생성 당시 검증한 명단으로 고정하며, 수신 시에도 해당 방의 현재 입장 완료 상태를 검사한다.

활성 안내는 방당 최대 20개, 선택 사용자는 요청당 최대 100명으로 제한한다. 유효기간이 겹치는 같은 방·앱 구분·플랫폼·업데이트 UUID의 업데이트 안내는 하나만 허용한다. 같은 업데이트를 다시 알리려면 기존 안내를 삭제한 뒤 새 안내를 생성한다. 두 요청의 결과는 각각 확인한다.

조회 인덱스는 활성 안내의 방·기간, 대상의 사용자·안내, receipt의 안내·사용자·설치 조합에 둔다. 운영 요청·감사·receipt는 90일 보관 후 정리한다. 안내와 대상 행은 만료 90일 후 연관 기록과 함께 정리하며, 별도 개인정보 복사 로그를 만들지 않는다.

## 6. 관리자 API와 채팅 도구

`supabase/functions/admin-toasts/`와 `scripts/admin-toasts.mjs`를 신설한다. API 계약이다. 실제 명령과 서버 준비 절차는 [운영 안내](../operations/ADMIN-TOASTS.md)를 따른다.

| 작업 | 동작 |
| --- | --- |
| `preview` | 입력, 대상, 배포 정보와 만료 시각 검증. DB를 바꾸거나 표시하지 않음 |
| `create` | 검증한 안내 생성·활성화. 요청 UUID 필수 |
| `delete` | 캠페인 ID와 요청 UUID로 삭제. 삭제 시각·이력을 남기며 복원 불가 |
| `list` | 방별 활성·예정·종료 안내 조회 |
| `status` | 요청 처리 결과 또는 안내 설정·관측 집계 조회 |

요청 예시의 식별자는 설명용 자리표시자다.

```json
{
  "action": "create",
  "requestId": "<요청 UUID>",
  "campaignId": "<안내 UUID>",
  "kind": "update_ready",
  "roomId": 1,
  "audience": "room",
  "deploymentRef": "<검증할 배포 기록 또는 Release>"
}
```

스크립트가 배포 기록을 해석해 완전한 대상 정보를 구성하고, 서버도 project·channel·runtime·UUID 형식과 허용 조합을 검증한다. 최초 구현은 성공한 배포의 `update-record.json`과 EAS 응답을 대조하고 Release의 그룹 참조와 연결한다. ‘이번 업데이트’가 여러 성공 배포 중 모호하면 후보와 시각을 제시해 대상을 확정한다. 실패·취소된 배포나 이름만 추정한 최신 업데이트를 등록하지 않는다.

동일 요청 UUID와 동일 입력은 기존 결과를 반환하고, 같은 UUID의 다른 입력은 409로 거부한다. 응답을 잃으면 같은 UUID로 `status`부터 조회한다. 새 UUID를 발급해 재발송하지 않는다. `delete`는 안내 ID와 요청 UUID만 사용한다. 이미 삭제된 안내에 대한 재요청도 삭제 시각을 바꾸지 않는다.

첫 요청은 preview로 대상과 설정을 확인한 뒤 사용자의 명시한 발송 범위 안에서 실행한다. 이미 구체적으로 지시한 작업에 불필요한 재확인을 요구하지 않는다. 누락된 대상·배포가 실제로 모호할 때만 확인한다.

전용 `yumyum-send-toast` 스킬에는 입력 해석, preview, 요청 ID 재사용, 결과 조회, 비밀값 비출력, 실패 복구를 정의한다. 관리자 토큰은 운영 비밀 설정에만 보관한다. 스크립트는 파일 입력을 사용해 문구·명단·인증값을 셸 보간하지 않는다.

## 7. 앱 조회와 실시간 수신

조회 API는 `get_admin_toasts()` RPC로 제공한다. 클라이언트가 보낸 room·userId를 권한 판단에 사용하지 않고, 서버의 `auth.uid()`와 현재 방 입장 검증으로 대상을 결정한다. 응답은 `server_now`, 대상 캠페인 목록, 각 revision을 포함한다. 서버 활성 설정과 개인정보 필터를 통과한 항목만 반환하고, 실제 기기 OTA 상태는 앱에서 판정한다.

조회 계기는 다음과 같다.

- 시작 화면 종료·인증·방 입장 완료 후 최초 조회.
- 앱 전경 복귀, 웹 탭 복귀, 네트워크·Realtime 재연결 직후 조회.
- `admin-toasts:room:<roomId>` private 채널의 `changed` 이벤트 수신 시 조회.
- 앱이 전경이면 정상 연결 상태에서도 60초 간격으로 조회. 배경에서는 중단.
- OTA 다운로드 완료·다운로드 대상 변경 시 최근 설정으로 재평가하고 필요하면 즉시 조회.

Broadcast에는 변경됐다는 정보와 방 범위만 싣는다. DB 트랜잭션의 변경 트리거로 신호를 내보내고 수신 앱은 저장된 목록을 다시 읽는다. 서버에서 소켓을 구독해 발송하는 구조는 피한다. DB 또는 HTTP Broadcast를 사용할 수 있다. [Supabase Broadcast 문서](https://supabase.com/docs/guides/realtime/broadcast)

실시간 연결을 먼저 시작하고 `SUBSCRIBED` 시 전체 조회한다. 동시 조회는 하나로 합친다. 조회 중 변경 신호가 오면 dirty로 표시해 다시 조회하며, 더 최신 변경을 알게 된 응답을 그대로 표시 기준으로 확정하지 않는다. 목록은 추가 병합이 아니라 서버 스냅샷으로 교체해 삭제 항목도 제거한다. 방·UID 변경은 generation을 증가시켜 이전 응답·이벤트·타이머를 무효화한다.

정상 온라인 상황에서 변경 후 3초 이내 수신·재평가를 목표로 하며, Broadcast 누락 시 다음 전경 조회로 보완한다. 이는 네트워크 장애 중 도달 보장이 아니다. 오류 재시도는 기존 공통 갱신 루프의 약 5·10·20·40·60초 백오프와 지터를 적용하고, 네트워크 복구 시 즉시 시도한다.

실패 시 미확인 안내를 새로 표시하지 않는다. 마지막 서버 확인 후 90초가 지나면 표시 중 관리자 안내도 일시 숨긴다. 서버 시간과 경과 시간을 이용해 만료를 계산하고 전경 복귀 때 다시 검증한다. 삭제·만료·대상 제외를 확인하면 표시·대기 항목을 제거한다. 원격 삭제는 오프라인 기기에 즉시 강제할 수 없다.

## 8. 표시 조건과 우선순위

표시 직전에 다음 조건을 모두 검사한다.

1. 현재 UID·방이 조회 당시 범위와 같고 인증·입장·시작 준비가 완료됐다.
2. 서버에서 활성·기간·대상 검증을 통과했고 설정 신선도가 유효하다.
3. 앱이 schema·kind·capability를 지원하며 플랫폼·앱 구분이 일치한다.
4. 동일 안내를 이 설치의 현재 사용자·방에서 완료하지 않았다.
5. 앱이 전경이고 키보드·모달·차단 오버레이가 없다.
6. 공부 중인 activeSession, 저장 작업, 방 전환, 업데이트 재시작이 진행 중이지 않다.
7. 업데이트 안내이면 다음 절의 OTA 조건도 만족한다.

공부·저장 중에는 서버 안내를 받아도 표시만 보류한다. 공부 기록이나 세션을 종료하지 않는다. 보류 상태는 미수신·읽음으로 처리하지 않는다. 조건 해제 시 다시 평가한다.

한 번에 관리자 안내 하나만 공통 호스트에 등록한다. 정렬은 업데이트 안내 우선, 이후 시작 시각·ID 순서다. 서버 후보가 많아도 공통 대기열에 한꺼번에 넣지 않는다. 이미 표시 중인 축하·사용자 작업 결과를 가로채지 않고 다음 표시 기회를 기다린다. 여러 활성 업데이트 안내가 있어도 실제 다운로드 대상과 맞는 한 건만 후보가 된다.

## 9. 지정한 OTA 업데이트 판정

SDK 58의 `Updates.useUpdates()`는 `downloadedUpdate`, `currentlyRunning`, `isUpdatePending`을 제공한다. `downloadedUpdate`의 업데이트 ID와 manifest를 활용해 읽기 전용 OTA 상태를 확장한다. 별도의 다운로드·재시작 루프를 만들지 않는다. [Expo SDK 58 Updates 문서](https://docs.expo.dev/versions/v58.0.0/sdk/updates/#useupdates)

업데이트 토스트의 추가 조건은 아래와 같다.

```text
native OTA enabled && production/test 구분 일치 && !development
&& isUpdatePending
&& downloadedUpdate.type == NEW
&& downloadedUpdate.updateId == campaign.targetUpdateId
&& currentlyRunning.updateId != campaign.targetUpdateId
&& 실제 플랫폼·channel·runtime이 검증한 배포 대상과 일치
```

필수 정보가 없으면 표시하지 않는다. available 상태만으로 ‘준비됐어요’를 표시하지 않는다. rollback-to-embedded는 일반 업데이트 안내에서 제외한다. 개발·Expo Go·웹에서는 실제 OTA 안내를 표시하지 않는다. Storybook은 명시적 모의 상태만 사용한다.

| 상황 | 결과 |
| --- | --- |
| A 다운로드 완료 후 A 안내 활성화 | 조회 후 표시 |
| A 안내 활성화 후 A 다운로드 완료 | 완료 시 표시 |
| A를 이미 적용한 뒤 A 안내 활성화 | 표시하지 않음 |
| B가 다운로드돼 있는데 A 안내 활성화 | 표시하지 않음 |
| A 표시 중 다운로드 대상이 B로 변경 | A 안내 제거. B 안내가 별도로 있어야 B 표시 |
| A 안내 삭제됨 | A 토스트 제거. 다운로드·적용하기는 유지 |
| 다음 앱 시작 때 A가 자동 적용됨 | 이미 실행 중이므로 A 적용 전 토스트는 표시하지 않음 |

`vX.Y.Z-rN`은 배포 기록 참조로만 사용한다. 리비전 문자열의 크기로 최신 여부를 비교하지 않고 APK 업데이트 안내와 혼동하지 않는다.

## 10. 기존 업데이트 토스트 연결

기존 시안의 제목·아이콘·X·바로가기·오류 표시를 유지한다. 미리보기 전용 휴대폰 프레임·조작 버튼은 실제 앱에 옮기지 않는다. 토스트는 자동으로 사라지지 않고 다음 경우 종료한다.

- 사용자가 X를 누름: 해당 설치에서 이 안내를 완료 처리.
- 바로가기 후 마이페이지 업데이트 영역이 실제 표시됨: 완료 처리.
- 관리자 삭제·만료·대상 상실·다운로드 대상 변경·적용 완료: 시스템 제거. 사용자 확인 완료와 구분.

바로가기는 Expo Router로 `/profile`에 이동하고 업데이트 행까지 스크롤한다. 현재 화면이 profile이면 중복 화면을 쌓지 않고 해당 영역을 표시한다. 경로 변경만으로 닫지 않고 목적지 영역의 layout·화면 표시 확인 신호를 받는다. `campaignId + generation + navigationAttemptId`를 함께 확인해 늦은 응답이 다른 안내를 닫지 못하게 한다.

목적지 확인 제한 시간은 5초다. 실패하면 기존 ‘업데이트 위치로 이동하지 못했어요. 다시 시도해 주세요.’를 표시하고 토스트를 유지한다. 중복 클릭은 막고 재시도할 수 있게 한다. 자동 적용이나 재시작을 호출하지 않는다. 접근성 초점 이동은 목적지 준비 후 처리하며 VoiceOver·TalkBack에서 확인한다.

아이콘 props는 native·web 공통 항목만 사용하고 레이아웃·transform은 View 래퍼에 둔다. 실제 토스트는 공통 호스트의 safe area·화면 크기·글자 확대·reduced motion 규칙을 따른다.

## 11. 중복 방지와 상태 전이

상태는 `received → waiting → presenting → completed`이며, 일시 차단은 `presenting → waiting`, 삭제·만료·조건 상실은 `removed`다. 일반 안내는 실제 표시 확인 시 완료로 기록하되 화면에서는 정해진 시간까지 유지한다. 업데이트 안내는 X 또는 목적지 표시 확인 시에만 완료한다.

로컬 저장 키는 `(installationId, uid, roomId, campaignId)`다. 설치 ID는 토스트 기능 전용 무작위 값이며 기기 고유 식별자를 수집하지 않는다. 기존 AsyncStorage를 이용하고 사용자 문구는 저장하지 않는다. 앱 재설치·저장소 초기화·다른 설치에서는 다시 표시될 수 있다. 계정 전체에서 정확히 한 번 표시하는 기능은 이번 범위가 아니다.

완료 시 로컬 저장을 먼저 시도하고 서버 receipt를 비동기 전송한다. 저장 실패는 현재 실행의 메모리 상태로 중복을 막으며 로그 코드만 남긴다. receipt 실패가 사용자 토스트를 반복시키지 않게 한다. 크래시와 저장 실패까지 포함한 정확히 한 번 표시는 보장하지 않는다. 같은 사용자라도 다른 기기의 미적용 업데이트 안내를 막지 않는다.

기존 store에 관리자 커스텀 토스트용 완료 기억 정책을 추가한다. 기본 동작은 유지하고 관리자 항목만 명시적으로 최종 완료된 경우 기억하게 한다. `blocked/background/scope/unmount/rejected`는 완료로 남기지 않는다. 기능 컨트롤러가 서버 후보와 로컬 기록을 보관해 다시 등록한다. 호스트가 숨겨질 때 `ToastSlot`을 재등록할 수 있도록 인스턴스 ID·재시도 시점을 관리한다.

컴포넌트 정리용 `dismiss()`와 사용자 X는 별도 이벤트로 취급한다. `onDismiss('manual')`만 보고 사용자 완료를 추정하지 않는다. X·목적지 준비 핸들러가 완료 기록을 명시적으로 남기고, lifecycle cleanup은 완료시키지 않는다. 서버 취소·OTA 대상 변경 역시 완료로 오인하지 않는다.

완료 기록은 해당 안내 만료 후 7일까지 보관하고 정리한다. 아직 유효한 기록을 개수 제한 때문에 버려 재표시하지 않는다. 삭제한 캠페인은 같은 ID로 복원하지 않는다. 다시 알리는 경우 새 ID로 생성하며 기존 완료 기록을 초기화하지 않는다.

## 12. 권한과 데이터 보호

- 관리자 쓰기는 전용 서버 인증으로만 허용한다. 앱 번들·공개 환경변수·문서에 관리자 토큰이나 서버 비밀 키를 넣지 않는다.
- 노출 스키마의 신규 테이블에는 RLS를 켜고 필요한 권한만 명시적으로 부여한다. `authenticated` 역할만으로 방 입장 권한을 대신하지 않는다.
- 조회는 현재 방 입장 완료 조건, 방 ID, 선택 사용자 소속을 서버에서 검증한다. 선택 명단 테이블은 본인 행만 조회 가능하게 하며 다른 대상 명단과 관리자 감사 기록을 노출하지 않는다.
- 기본 조회 RPC는 `SECURITY INVOKER`와 테이블 RLS를 사용한다. 권한 상승이 필요한 내부 트리거·관리 함수는 비노출 스키마와 최소 EXECUTE 권한으로 제한하고 빈 search_path·완전 수식 이름을 적용한다.
- 일반 앱의 캠페인 생성·수정·타인 receipt 기록·Broadcast 발행은 금지한다. 방 채널은 입장한 방 수신만 허용한다. 기존 `realtime.messages` 정책의 OR 결합까지 검사해 다른 발행 정책이 새 topic을 허용하지 않게 한다.
- receipt RPC는 UID를 서버에서 결정하고 안내 대상 자격, event 종류·시각·installationId 길이를 검사한다. 삭제되거나 방을 옮긴 사용자의 뒤늦은 제출은 거부한다.
- 실시간 채널 권한은 접속 시 평가되므로 방 전환·인증 변경 때 구독을 제거하고 재인증한다. 신호 자체에는 개인정보가 없고 본문은 매번 서버 권한 검증 후 읽는다.
- 요청 크기·텍스트 길이·대상 수·기간·활성 개수 제한과 rate limit을 적용한다. 감사 로그에는 토큰·구독 키·불필요한 개인 명단을 저장하지 않는다.
- 배포 전 다른 방·미입장·다른 사용자·anon·일반 authenticated의 거부 테스트와 Supabase advisors 확인을 완료한다.

## 13. 운영 결과와 관측

활성화 응답에는 안내 ID, 종류, 방, 대상 방식·현재 대상 수, 시작·종료 시각, 업데이트 식별 정보, 처리 결과를 표시한다. 대상 수는 설정 시점의 자격 수이며 온라인 수·실제 표시 수가 아니다.

status는 `서버 활성화`, `표시 보고 설치 수`, `종료 보고 설치 수`, `사용자 수`를 구분한다. 업데이트 다운로드 여부는 기기에서 판정하므로 preview가 실제 표시 가능 인원을 단정하지 않는다. receipt는 앱 보고 관측치이며 강제 읽음 증명이나 발송 도달 보장이 아니다.

관측 오류 코드는 인증 실패, 대상 없음, 미지원 템플릿, 배포 대상 불일치, 목록 조회 실패, 로컬 저장 실패, 목적지 이동 실패, receipt 실패로 나눈다. 사용자에게 서버 조회 오류 토스트를 반복 표시하지 않고 앱 로그와 관리자 조회에서 진단한다.

## 14. 구현 파일과 작업 순서

| 단계 | 작업과 산출물 |
| --- | --- |
| 1 | DB 모델·RLS·private 변경 신호·조회/receipt RPC·관리 트랜잭션과 권한 테스트 |
| 2 | `supabase/functions/admin-toasts/`, `scripts/admin-toasts.mjs`에 preview/create/delete/list/status와 멱등성 구현 |
| 3 | `src/features/admin-toasts/`에 model, API, 수신 훅, 순수 eligibility 판정, 로컬 기록, controller, Provider 추가 |
| 4 | OtaUpdateProvider에 읽기 전용 대상 정보 추가, `_layout.tsx`의 OtaUpdateProvider 내부에 관리자 Provider 연결 |
| 5 | UpdateToast 표시 컴포넌트 추출, Profile 업데이트 행 위치·준비 신호, 토스트 store의 완료 정책 확장 |
| 6 | 기존 Storybook을 실제 공유 컴포넌트로 교체하고 일반 안내·대기·복구 사례 추가 |
| 7 | 전용 `yumyum-send-toast` 스킬과 `docs/operations/ADMIN-TOASTS.md` 운영 안내 작성 |
| 8 | 테스트 방 검증 → develop PR → 기존 운영 배포 절차 → 안내 수신 기능 반영 → 운영 안내 활성화 |

필요한 라이브러리는 이미 있는 Supabase client, Expo Updates, AsyncStorage, Expo Router, 공통 토스트를 사용한다. 현재 설계에 신규 native 모듈은 필요하지 않다. OTA 호환성은 실제 변경 후 기존 release review로 판단하며 문서 단계에서 APK 불필요를 확정하지 않는다.

최초 출시에서는 서버를 먼저 추가하되 운영 안내는 아직 생성하지 않는다. 기능이 없는 구버전 앱은 이 안내를 받을 수 없다. 수신 기능을 배포한 후 테스트 방에서 일반 안내와 다음 테스트 OTA를 검증하고 운영 대상에 활성화한다. 앱이 이번 기능 업데이트를 적용하기 전, 그 업데이트를 안내하도록 소급 지원할 수는 없다.

롤백은 진행 중인 관리자 안내 삭제를 우선 사용한다. 이 조작은 기존 OTA 다운로드·수동 적용·푸시 알림을 중단하지 않는다. 서버 장애 시 앱은 관리자 안내만 숨기고 공부·저장 기능을 계속 제공한다.

| 검증 분야 | 필수 사례 |
| --- | --- |
| 운영 API | 동일 요청 재시도 1건 처리, 해시 충돌 409, 삭제 재시도, 발송 결과 불명 시 status 복구, 재발송 명시 여부 |
| 권한 | 0·1번방 격리, 미입장 거부, 선택 대상 외 조회 거부, 명단 누출 없음, 앱 쓰기·Broadcast 위조 거부 |
| 시각 | 시작 직전/정각, 만료 정각, 클라이언트 시계 차이, 실행 중 예정 안내 시작, 만료 후 대기·표시 제거 |
| 수신 | 시작/복귀/재연결, 구독과 조회 사이 변경, 이벤트 중복·누락·폭주, 조회 중 삭제, 오래된 응답 무시 |
| 업데이트 | 배포 전/후 활성화, 다운로드 전/후 활성화, 적용 완료, 다른 UUID, runtime/channel/variant 불일치, rollback, 대상 교체 |
| UX | 공부·저장·키보드·모달 중 보류, 조건 해제 후 표시, 축하 토스트와 순차 표시, X, 목적지 확인·실패·재시도 |
| 중복 | 앱 재실행, 삭제 후 재노출 금지, 다른 사용자·방·설치 격리, local 저장 실패, receipt 재전송, 일시 숨김 뒤 복구 |

| 접근성 | 화면 읽기 제목·버튼·상태 전달, 최소 터치 영역, reduced motion, 목적지 초점 |

순수 controller·eligibility·멱등성과 권한 경계는 모의 테스트 및 로컬 DB 통합 테스트로 검증한다. lint와 typecheck를 실행하고, Storybook을 시각 확인한다. Android 실제 OTA 흐름과 native 화면은 실제 수행 결과를 남긴다. native 시각 확인을 하지 않았으면 완료 기록에 그 한계를 명시한다.

사용자가 “배포한 업데이트 안내 켜줘”라고 했을 때 정확한 배포 대상을 선택해 서버 활성화 결과를 돌려주고, 미적용 대상 앱만 기존 토스트를 받으며, 일반 안내도 같은 관리자 경로로 독립적으로 보낼 수 있으면 기능 완료다.
