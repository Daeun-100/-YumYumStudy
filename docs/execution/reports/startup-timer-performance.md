# 초기 진입 및 타이머 시작 성능 개선 (1~3단계)

## 변경

- 시작 요청과 이전 시작 요청 복구에서 `ensure_profile` 재호출을 제거했다. 앱 부팅 중 서버가 확인한 사용자 ID를 방별 메모리에 보관하고, 시작 시 현재 인증 세션의 ID와 비교한다. 세션 없음·사용자 불일치·인증 오류는 요청을 보내지 않고 실패한다. 서버 RPC의 인증/권한 검사는 그대로다.
- 초기 복구를 완료한 후 첫 스냅샷을 조회하는 경로 하나로 통합했다. 복구 중에는 실시간/복귀/네이티브 감시 갱신을 활성화하지 않는다.
- 동시에 들어온 조회는 진행 중인 Promise를 공유한다. 시작·중지 시 세대를 바꿔 이전 조회를 재사용하거나 오래된 응답을 반영하지 않는다. 조회 중 실시간 변경/복귀 이벤트가 오면 후속 조회를 한 번 예약하여 변경을 놓치지 않는다.
- 서버 시작 확정과 필요한 네이티브 감시 연결 이후 타이머를 반영한다. 후속 전체 조회는 버튼의 완료를 막지 않는다(기존 동작 유지).

## 기록 보호

기존의 시작 전 요청 ID 영구 저장, 중복 클릭 잠금, 응답 불확실 시 같은 ID 재사용, 앱 재실행 복구, 응답 소유자 검증을 유지했다. 서버 스키마와 기록 계산 규칙은 변경하지 않았다.

## 기기에서 측정하기

측정 코드는 외부 전송 없이 최근 200개 표본을 메모리에 보관한다. 사용자 ID, 토큰, 요청 인자, 오류 본문은 저장하지 않는다. `src/lib/performance.ts`의 `getTimingSamples()`로 표본 복사본을 얻을 수 있다.

테스트 실행/빌드 환경에 `EXPO_PUBLIC_PERFORMANCE_LOGS=true`를 설정하면 각 표본이 `[study-performance]` 접두사로 콘솔에 출력된다. Expo의 공개 환경 변수는 번들 생성 시 반영되므로 이미 배포한 앱에 소급 적용되지는 않는다. 기본값에서는 표본을 콘솔에 출력하지 않는다.

- `identity.verify`: 부팅의 서버 인증 확인. 기존 초기화 구조상 프로필 준비 중 재확인도 별도로 보일 수 있다.
- `startup.admission`, `startup.profile`: 입장 및 프로필 준비.
- `identity.session`: 시작/복구 때 현재 세션과 검증된 사용자 비교. 만료 시 세션 갱신 시간이 포함될 수 있다.
- `startup.recover`, `startup.study`: 이전 시작 복구 및 복구+초기 스냅샷 전체 시간.
- `startup.visible`: StartupBoundary가 마운트된 뒤 이미지 준비와 화면 공개까지. 입장 게이트 이전 시간이나 OS 앱 실행 시간은 포함하지 않는다.
- `rpc.get_today`, `rpc.get_room`, `rpc.get_history`, `rpc.start_study`, `rpc.stop_study`: 각 서버 요청 시간. 동시 요청 시간은 합산하지 않는다.
- `study.reconcile`, `study.refresh`: 기기 기록 동기화 및 스냅샷 갱신.
- `timer.status`, `timer.transport`, `timer.prepare`, `timer.bind`, `timer.toggle`: 기기 설정, 감시 연결 준비/완료 및 시작·중지 버튼 전체 처리 시간. `timer.toggle`에는 후속 스냅샷 갱신이 포함되지 않는다.

동일한 기기·네트워크에서 앱 완전 종료 후 실행, 재실행, 시작/중지 반복을 각각 측정한다. 감시 권한을 허용한 모드와 기본 모드, 정상 연결과 오프라인 후 복구도 구분한다. 중앙값과 느린 실행의 값을 비교한다. 현재 자동 테스트는 안전성과 중복 호출 억제를 검증하며, 실제 기기의 개선 시간은 아직 측정하지 않았다.

## 검증

자동 테스트는 초기 복구 선행 및 초기 조회 1회, 동시 조회 공유, 변경 이벤트 후속 조회, 시작·중지 세대 분리, 오래된 응답 차단, 중복 시작 잠금, 인증 소유자 불일치 차단을 검증한다. 기존 시작 테스트는 응답 유실·재실행·저장 실패·오프라인 반복에서도 요청 ID가 유지되는지 검증한다.

## 2026-10-27 측정 결과 (휴대폰 연결 없이 가능한 범위)

ADB 연결 기기가 없고 Android 에뮬레이터도 설치되어 있지 않아 네이티브 앱 실행 측정은 하지 못했다. 아래는 앱의 개선 전후 비교가 아니라 실제 서버의 누적 DB 통계와 현재 Mac의 HTTPS 측정이다. 사용자·공부 기록 생성 및 변경 없이 읽기 전용으로 확인했다.

### 실제 RPC의 누적 DB 실행 통계

동일 프로젝트의 `extensions.pg_stat_statements`에서 PostgREST RPC 호출만 조회했다. 통계 초기화 시각은 2026-10-26 00:12:51 KST다. 방별·앱 버전별 구분은 없으며 휴대폰 네트워크, API 게이트웨이, 인증, 네이티브 모듈, 화면 렌더링 시간은 포함하지 않는다. 최대값은 현재 지연이나 흔한 지연을 의미하지 않는다.

| 요청 | 호출 수 | 평균 DB 실행 | 최대 DB 실행 |
| --- | ---: | ---: | ---: |
| 오늘 기록 `get_today` | 5,725 | 10.71ms | 3,030.27ms |
| 친구 현황 `get_room` | 5,721 | 13.02ms | 3,209.51ms |
| 기간 기록 `get_history` | 3,187 | 8.28ms | 1,027.35ms |
| 시작 `start_study` | 57 | 13.95ms | 62.91ms |
| 중지 `stop_study` | 33 | 5.67ms | 28.47ms |
| 프로필 `ensure_profile` (방 인자 포함) | 1,187 | 2.40ms | 138.15ms |
| 입장 `get_onboarding` | 175 | 4.49ms | 91.32ms |

### 현재 Mac → 서버 HTTPS 요청 10회

공개 Auth 설정 조회(`/auth/v1/settings`)를 순차 호출하고 응답 본문을 모두 읽을 때까지 측정했다. 인증된 기록 RPC의 시간과 동일시할 수 없다. 첫 요청은 201.61ms, 이후 9회 중앙값은 69.20ms, 범위는 58.22~98.62ms다.

전체 표본(ms): 201.61, 69.29, 69.20, 98.62, 75.72, 58.59, 58.79, 82.60, 58.22, 59.56.

### 해석 및 남은 측정

누적 통계에서 시작 RPC의 DB 실행 자체는 평균 약 14ms였다. 따라서 버튼 체감 지연을 DB 계산만으로 설명할 근거는 부족하다. 순차 인증 요청, 휴대폰 네트워크, 네이티브 감시 준비가 차지하는 시간은 기기 측정이 필요하다. 기록 조회는 평균 수 ms~십여 ms지만 최대 1~3초의 지연 이력이 있어 간헐적인 DB 지연도 배제할 수 없다. 개선 효과의 ms 또는 비율은 아직 산출하지 않았다.

휴대폰 연결 후 측정 로그를 활성화한 테스트 앱에서 첫 실행·재실행·시작·중지를 반복하고, 같은 조건의 이전 코드와 비교해야 한다.

## 4~5단계 구현

앞부분의 초기 구현 설명 중 첫 화면 이미지 준비 대기는 아래 변경으로 대체됐다.

- 내 `get_today` 조회·기기 복구와 친구 `get_room` 조회를 독립시켰다. 초기 복구와 내 실시간 스냅샷이 준비되면 첫 화면을 공개하며, 친구 조회 또는 친구 조회 오류는 화면 공개를 막지 않는다. 친구의 로딩·오류·재시도는 별도로 관리한다.
- 전체 배경/캐릭터 이미지의 숨김 사전 로딩 완료 조건을 제거했다. 화면은 기존에 마운트된 상태로 이미지를 로딩하며, 내 실시간 상태 반영 후 두 프레임을 거쳐 공개한다.
- 최근에 조회한 내 기간별 기록 요약을 기기에 저장한다. 프로젝트·사용자·방·조회 범위를 분리하고, 최대 24개 범위와 저장 후 7일 제한을 둔다. 손상된 값, 중복 날짜, 범위 밖 날짜, 이전 스키마는 복원하지 않는다.
- 디스크 복원과 서버 조회는 동시에 시작한다. 복원된 요약을 먼저 표시하고 서버 응답으로 교체한다. 캐시 읽기/쓰기 실패가 서버 조회를 막지 않으며, 늦게 도착한 캐시가 최신 서버 응답을 덮어쓰지 않는다. 캐시 데이터 표시 중에는 이를 알리는 문구를 표시한다.
- 캐시된 요약 자체는 실행 시간을 추가하지 않는다. 오늘의 더 최신 실시간 스냅샷이 있으면 그 데이터로 오늘 기록을 표시한다. 타이머 실행 상태, 시작 요청 ID, 친구 기록, 상세 세션은 이 영구 캐시에 넣지 않는다. 일별 상세 세션은 별도로 조회하므로 요약 표시를 막지 않는다.
- 기록 조회 도중 시작·중지 등에 의해 로더가 바뀌면 후속 조회를 예약하고 이전 결과를 화면에 반영하지 않는다. 친구 조회에도 세대를 적용해 타이머 조작 이전 응답이 이후 응답을 덮어쓰지 않게 했다.

### 보존한 타이머 대기

Android 감시 상태 확인·준비 → 서버 시작 확정 → 감시 연결 순서는 유지한다. 1~3단계에서 반복 인증·프로필 조회를 줄였지만, 4~5단계는 이 네이티브 시작 순서를 단축하는 작업이 아니다. 감시/서버 확인을 생략하거나 영구 캐시의 실행 상태로 타이머를 시작하지 않는다. 따라서 이 구간이 느릴 때 재생 로딩이 남을 수 있으며, 실기기 측정 전에는 재생 로딩 해결이나 속도 개선 비율을 주장하지 않는다.

### 검증

친구 응답 지연/실패 상태에서 내 초기화 및 중복 없는 시작, 친구만 재시도, 내 실시간 응답이 없을 때 시작 차단, 시작 전후 친구 응답 순서 역전, 초기 화면의 이미지·친구 의존성 제거를 자동 테스트했다. 디스크 재실행 복원, 사용자/방/범위 격리, 만료/손상 데이터 제외, 저장 오류, 늦은 캐시 및 메모리 퇴출 경합, 기록 조회 중 변경 이벤트도 검증했다. lint·타입 검사 및 테스트용 웹 번들 export가 통과했다. 실기기 테스트와 배포는 진행하지 않았다.
