# 성취 알림 지연 측정

## 개선 적용 후

공통 호스트 분리 이후 스크립트의 마운트 값은 성취 제어기의 토스트 등록 요청 준비 시점까지를 뜻한다. 공통 대기열이 비어 있지 않으면 앞선 토스트를 기다리며, 실제 호스트의 React 렌더링·실기기 표시 프레임 시간은 이 모의 측정에 포함하지 않는다.

목표 도달 전 현재 포그라운드의 서버·가드 정산이 끝난 경우, 목표 도장 표시를 서버 요청에서 분리했다. 주간 스탬프와 날짜 중복 마커는 미리 조회한다. 보상 발급은 서버 확인 이후 같은 토스트에서 전환하며, 도장 연출 후 기본 4초 + 보상 후보일 최대 2초 대기까지만 허용한다. 복귀 직후에는 정산을 먼저 수행한다.

동일 컨트롤러 벤치마크를 개선 코드로 다시 실행했다. 저장소 읽기 모의 객체의 default import를 바로잡고, 5ms 읽기가 목표 도달 전에 완료되도록 준비했다. 아래 시간은 단순 hook 런타임에서 목표 도달부터 첫 토스트 마운트까지이며, 휴대폰 화면 표시 시간이 아니다.

| 응답 지연 주입 조건 | 첫 도장 마운트 |
| --- | ---: |
| 요청당 100ms · 목표/보상 | 약 4ms |
| 요청당 500ms | 약 4ms |
| 요청당 1,500ms | 약 4ms |
| 연차만 1,500ms | 약 4ms |
| 요청당 100ms + 다음 틱 900ms | 약 904ms |
| 연차 조회 실패 | 목표 도장 유지 |

서버 지연이 첫 도장 표시를 막지 않음을 확인했다. 1초 간격 감지와 React Native 렌더링·애니메이션 시간은 별도로 남는다. 초기/복귀 정산 시간도 즉시 표시 경로의 수치에 포함되지 않는다. 보상 확인이 늦거나 실패해도 목표 축하가 사라지지 않으며, 이미 닫힌 토스트는 되살리지 않는다.

서버 확인 전·후 승격, 실패 후 늦은 기록 응답, 4초 기본/2초 추가 대기, 자동 소멸, 백그라운드 응답 무효화는 결정적 회귀 테스트로 검증한다.

아래는 개선 전 조사 기록이다. 현재 스크립트는 개선 후 동작을 측정한다.


측정: 2026-10-29 16:08 KST. 대상: `codex/achievement-toasts`, `564f121`의 표시 흐름. 알림 동작은 변경하지 않았다.

## 결론

현재 목표 달성 알림은 오늘 재확인과 주간 기록·연차 조회를 기다린다. 보상이 없는 날도 연차 조회 지연·실패의 영향을 받는다. 즉시 표시는 보장되지 않는다.

정상적으로 JS가 실행되는 포그라운드에서 전체 대기 경로는 다음과 같다.

`다음 시계 틱 대기(0~1초) + 기기 저장소 읽기 + confirmToday + max(이번 주 기록 조회, 연차 조회) + 렌더링`

`confirmToday` 안에는 오늘 조회 외에 Android 네이티브 상태 확인·정산이 들어갈 수 있다. 화면 등장은 이후 시작하며, 등장 애니메이션 완료까지 380ms, 도장 동작 완료까지 760ms이다. 처음 보이는 시점은 애니메이션 완료보다 빠르다. 모달·키보드·백그라운드에서는 의도적으로 표시를 보류한다.

## 실제 서버 로그

Supabase 연결 도구로 조회 시점 직전 24시간의 HTTP 200 응답을 집계했다. 아래는 게이트웨이 로그의 `response.origin_time` 기준이며 휴대폰에서 측정한 전체 왕복 시간이 아니다. 기록 조회는 다양한 기간의 기존 요청이 함께 포함되어 있어 이번 주 조회 전용 분포가 아니다.

| RPC | 표본 | 중앙값 | 평균 | P95 | 최대 |
| --- | ---: | ---: | ---: | ---: | ---: |
| get_today | 1,797 | 60ms | 218.23ms | 780.4ms | 12,735ms |
| get_history | 631 | 61ms | 167.26ms | 399.5ms | 8,703ms |
| get_leave_status | 723 | 65ms | 267.24ms | 787.8ms | 14,261ms |

각 함수의 통계는 개별 요청 기준이다. 중앙값·P95·최댓값을 더해 실제 한 사용자의 전체 알림 지연 분포라고 해석하면 안 된다. 느린 요청의 원인은 이번 측정으로 확정하지 않았다.

## 현재 알림 컨트롤러 실행 실험

실제 `AchievementCelebrations.tsx`를 TypeScript로 변환해 기존 hook 테스트 런타임에서 실행했다. 2시간 직전에는 토스트가 없는지 확인하고, 2시간에 도달하도록 앱 시계를 진행했다. 네트워크·저장소·환경만 대체했으며 실제 판정 모델과 표시 요청 순서를 사용했다. 아래는 RPC 지연을 주입한 각 1회 측정으로 실제 네트워크 속도 측정이 아니다. 모달 없음, Android 정산 없음. 초기 측정의 저장소 mock import가 맞지 않아 저장소 실패 시 메모리 경로가 사용되었다. 저장소 5ms는 개선 후 재측정에서 올바르게 적용했다. 소수 ms 차이는 타이머·런타임 편차다.

| 주입 조건 | 목표 도달부터 토스트 마운트까지 |
| --- | ---: |
| 네트워크 지연 0ms | 25ms |
| 요청당 100ms · 목표만 | 202ms |
| 요청당 100ms · 보상 포함 | 205ms |
| 요청당 500ms · 목표만 | 1,003ms |
| 요청당 1,500ms · 목표만 | 3,002ms |
| 오늘·기록 100ms, 연차만 1,500ms · 목표만 | 1,603ms |
| 요청당 100ms + 다음 시계 틱까지 900ms | 1,104ms |
| 연차 조회 실패 · 목표만 | 표시 안 됨; 이후 갱신·복귀의 재시도 필요 |

이로써 `오늘 확인 → 기록과 연차 병렬 조회 → 표시` 순서와, 일반 목표 알림까지 연차 응답을 기다리는 동작을 재현했다. 실제 React Native 렌더러·화면 프레임 시간은 포함하지 않았다.

재실행:

```bash
node --experimental-strip-types scripts/benchmark-celebration-latency.mjs
```

결과 JSON은 `/private/tmp/celebration-latency-results.json`에 기록한다.

## DB 함수 자체 실행 시간

동일 프로젝트에서 공부 세션 수가 가장 많은 온보딩 완료 프로필을 선택해 각 함수를 10회 실행했다. UUID·기록 내용은 출력하지 않았다. 한 트랜잭션에서 실행하고 마지막에 `ROLLBACK`하여 연차 정산을 포함한 변경을 남기지 않았다. 동일 트랜잭션의 캐시·재호출 효과가 포함되며 독립된 신규 보상 발급 10건의 측정은 아니다.

| 함수 | 평균 | 최대 |
| --- | ---: | ---: |
| get_today | 0.92ms | 4.21ms |
| get_history · 이번 주 | 1.27ms | 2.26ms |
| get_leave_status | 3.86ms | 6.60ms |

SQL 함수 내부 실행 시간은 게이트웨이·통신·앱의 전체 대기 시간을 나타내지 않는다.

## 남은 측정

실제 휴대폰에서 목표 도달부터 첫 표시 프레임까지의 시간, Wi-Fi/LTE 환경별 왕복 지연, Android 가드 정산 지연은 아직 측정하지 않았다. 일반적인 전체 지연을 확정하려면 실기기에서 이 세 지점을 함께 기록해야 한다.
